1. OBJECTIVE
   - Build the first incremental chunk of the Authentication & RBAC module.
   - Implement the public student registration endpoint (`POST /api/v1/auth/register`)
     along with Zod schema validation, data repository layer, service business logic,
     and HTTP controller.

2. WORK PERFORMED & ARCHITECTURE DETAILS
   - Created Zod validation schema `registerSchema` in `src/modules/auth/auth.schema.js`:
     * Validates `universityId` (UUID format), `rollNumber`, `email`, `password` (min 8 chars),
       `fullName`, and optional `phone`/`gender`.
   - Created `src/modules/auth/auth.repository.js`:
     * Structured repository with Map-based in-memory indexing by user ID, email, and roll number.
     * Implemented `findById`, `findByEmail`, `findByRollNumber`, and `createUser`.
   - Created `src/modules/auth/auth.service.js`:
     * Checks email and roll number uniqueness against the university ID.
     * Hashes passwords using Argon2id.
     * Sets default user status to `pending_verification` and role to `student`.
     * Implemented `sanitizeUser` helper to strip sensitive fields (`passwordHash`, `totpSecret`).
   - Created `src/modules/auth/auth.controller.js`:
     * Handles `POST /api/v1/auth/register` with `sendCreated(res, user, message)`.
   - Created `src/modules/auth/auth.routes.js`:
     * Configured `router.post('/register', validate(registerSchema), authController.register)`.
   - Mounted auth router in `src/app.js` under `/api/v1/auth`.

3. WHY BEHIND THE CHANGE
   - Step-by-Step API Development: Building APIs one by one in isolated chunks ensures each
     endpoint has dedicated validation, repository queries, error handling, and test coverage.
   - Pending Verification Initial State: New student registrations cannot immediately book beds
     or request gate passes until verified, protecting university residential boundaries.
   - Sanitization by Default: Removing password hashes and internal token hashes before returning
     user objects prevents accidental exposure of security credentials.

4. WHY NOT THE ALTERNATIVE(S)
   - Alternative 1: Building all auth endpoints in one monolithic commit/file.
     * Why Rejected: Violates incremental development guidelines and makes code review
       complex and error-prone.
   - Alternative 2: Allowing immediate 'active' status on self-registration.
     * Why Rejected: Violates SRS v2 security requirements where student identities must be
       verified or pre-seeded by administrators.
